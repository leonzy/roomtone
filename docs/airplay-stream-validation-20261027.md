# AirPlay 卡顿与转移后音量错误（2026-10-27）

验证对象：`708ec132` 加未提交工作树，Windows amd64、Go 1.26.10、本机 Flutter Web。未提交、推送或发布。

## 已发现与修改

1. 截图中的“播放设备不存在”是音量面板缓存了旧成员。日志显示转移到 9764 后，PATCH 仍指向目标组中的 9EC4（404）。区域切换或成员变更现在销毁/重置音量状态、清除防抖与待提交值，并拒绝过时异步结果；提交前检查成员身份。
2. 服务端分发器每帧 882 个采样，旧 RAOP 发送端将它切成 352/352/178，而 SDP 协商帧长为 352。现在跨分发帧缓存余数，只发送完整 352 采样包；明确的采样跳变清除余数。
3. 旧发送端没有读取 RAOP 控制端口的丢包请求。新增 1024 包有界缓存，按接收端请求回发原始加密 RTP 包；处理 16 位序号回绕，不推进正常流计数，过期包不误发。
4. 新增 15 秒 RTSP OPTIONS 保活，等待控制响应不占用 PCM 写锁；结束会话停止保活。原日志约 34 秒时 TEARDOWN EOF 提示控制连接可能已关闭，但**尚未证明空闲超时是本次卡顿根因**。

## 离线验证

- 176 个 20ms 分发帧（3.52 秒）得到 441 个完整 RTP 包；样本和时间戳连续。对加密 ALAC 实际 UDP 回环收包、解密，再由 FFmpeg 解码，PCM 与原输入逐字节一致。
- 使用 overlay 仅恢复旧分包方法，新回归按预期失败：第 3 包 724 字节（178 采样），不是 1420 字节（352 采样，L16 测试路径）。证据：本机工具目录 `short-packet-before.log`。没有替换运行服务进行反证。
- 模拟丢包请求覆盖 65534、65535、0 序号回绕；补包与原加密 RTP 逐字节一致，正常发送位置不变。保活仅连接本机假 RTSP 接收端。
- 前端新增回归覆盖同组拆成员、切换区域前有未提交拖动的情况；目标音箱正确，旧音箱不再收到请求。
- `TEST_FFMPEG` 开启的 app/player 全部定向 Go 测试、相关 vet 与 Dart 分析通过。输出模块完整测试结果见本机 `output-regression-20261027.log`。

## 未验收

用户要求不要再测试播放，本轮没有主动向真实音箱起播或执行播放转移。真实网络丢包率、音箱对短包的具体处理、修正后的听感与长时间播放均为 **Not run**。这些缺陷已用离线测试证明并修正，不能据此宣称实际卡顿已完全消失。原服务指标 underruns/dropped_frames 为 0，只覆盖解码/分发计数，不代表 RTP 网络无丢包。
